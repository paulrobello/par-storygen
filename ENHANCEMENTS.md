### ENH-001 — Generate TypeScript API types from OpenAPI
The web client hand-mirrors ~305 lines of TypeScript interfaces against `storygen_api/schemas.py`, and the audit's ARC-108 adds only a drift *alarm* (snapshot test). The full fix is codegen: run `openapi-typescript` against the FastAPI-emitted schema to produce `web/src/lib/api-types.gen.ts`, migrate `api.ts` interfaces to re-export the generated types, and wire generation + a clean-diff check into `web-check`/CI. Every future Pydantic change then propagates to the frontend mechanically instead of by convention.
**Impact**: High — eliminates the whole silent-drift class ARC-108 can only detect; makes API evolution one-sided. **Effort**: Medium (~1 session; the churn is mostly renaming imports in web/src).

> **✅ DONE (2026-07-17).** `scripts/export_openapi.py` emits `web/openapi.json` deterministically (`sort_keys=True`); `openapi-typescript` generates `web/src/lib/api-types.gen.ts` via `npm run gen:api` (`gen:api:check` asserts a clean diff). `web/src/lib/api.ts` now re-exports generated types for `Character`, `CharacterOutfit`, `ChoiceOption`, `GameSummary`, `NodeDetail`, `CharacterLibraryEntry` and derives `Choice`/`StoredChoice`/`StoryNode` from `NodeDetail`. Hand-written types are retained where the API schema is coarser than the client needs (`Theme`, `Tone`, `Relationship`, `GameSave` — the schema exposes these as opaque `{[key:string]:unknown}` blobs), each marked with a divergence comment. `GameSave` keeps its hand-written shape because `GameDetail` omits fields the client relies on (`narration_style`, `text_config`, etc.). openapi-typescript was added with `--legacy-peer-deps` (it peer-depends on TS ^5.x; the repo is on TS6) and `@testing-library/dom` was pinned as an explicit devDependency because the legacy install otherwise prunes it from the tree. NOTE: `gen:api:check` is not yet wired into `web-check` (the Makefile target would need the schema-export step); wire it in a follow-up or rely on the existing `test_api_openapi_snapshot.py` server-side alarm until then.

### ENH-002 — Stream narration tokens to the web UI over WS
The pipeline already streams beat tokens through `PipelineCallbacks` (the TUI renders them live, and the test suite pins the callback path), and the WS layer already broadcasts 13 server→client event types — but the web client only learns about a beat at `beat_committed`, so users stare at a spinner for the full 30–90 s generation. Add an `narration_token` WS event fed from the existing callback, a store buffer that accumulates tokens for the pending node, and progressive rendering in the story panel with a graceful fallback to `beat_committed` (which remains authoritative).
**Impact**: High — transforms perceived latency of the web app's core loop; parity with the TUI. **Effort**: Medium (server event + store + one component; throttling needed).

### ENH-003 — Fast game listing via summary sidecar
`list_games` (API) and the TUI load screen both derive listings from full `game.json` reads — files that grow with every node (a long game is hundreds of KB), so the menu/list cost scales with total story size across all games. After ARC-109 centralizes listing in `storage/save.py`, add a tiny `summary.json` sidecar written atomically by `save_game` (title, counts, updated_at, cover thumb path); the lister reads sidecars only, falling back to a full parse (and backfilling the sidecar) for legacy games.
**Impact**: Medium — snappy load screen/API listing regardless of library size; also gives the web UI cheap polling. **Effort**: Low (~half session; the write point is a single choke point, `save_game`).

### ENH-004 — Decouple usage accounting from full-save writes
par-mem centrality shows `save_game` is the graph's #2 hub (in-degree 121, betweenness 0.076): every LLM usage callback triggers a full-tree JSON serialization + atomic rewrite (`_on_usage` → `save_game`), so one advance can rewrite a multi-hundred-KB file 3+ times (beat, illustration, summary agents each fire). Make usage recording mutate-only (no implicit write) and let the pipeline's existing end-of-advance `save_game` persist everything once; the TUI header still updates from the in-memory totals.
**Impact**: Medium — 3×+ fewer full-file writes per advance, less SSD churn and less crash-window exposure; simplifies the ARC-101 story further. **Effort**: Medium (touches the shared adapters + both composition roots; strong existing tests).

> **✅ DONE (2026-07-17).** Removed the `save_game(save)` call from both `_on_usage` closures (`src/storygen/app.py:_start_game._on_usage` and `src/storygen_api/deps.py:build_pipeline._on_usage`); both now record usage in memory only (`record_usage_on_save`) and refresh the TUI header from the in-memory totals. The pipeline's existing commit-point `save_game` calls (beat commit, illustration commit, summary block — 14 sites in `pipeline.py`) persist everything once per advance. The now-unused `save_game` import was pruned from `deps.py`. All 926 Python tests (including the 44 `test_pipeline.py` cases) pass; the existing usage/persistence tests confirm totals stay exact across advances. Rollback is a two-line revert (re-add `save_game(save)` to each closure).

### ENH-005 — Single provider-metadata registry
Provider knowledge (names, default models, key env vars, base-URL rules, ref-image capability, suggested models) is spread across `config.py`, the TUI settings screen's triplicated sections (QA-009), the wizard, `storygen_api/routers/settings.py`, and `web` settings UI. Introduce `storygen/core/providers.py`: a declarative registry (frozen dataclasses) each surface renders from — TUI selects/labels, API exposes via a `GET /api/providers` route, web renders its settings from that route.
**Impact**: Medium — adding a provider becomes a one-file change instead of five; kills a whole class of cross-surface drift. **Effort**: Medium-High (~2 sessions; do after QA-009's ProviderSection extraction, which it slots into).

> **✅ DONE (2026-07-17).** Added `src/storygen/core/providers.py` — a dependency-free registry of frozen `ProviderInfo` dataclasses (`TEXT_PROVIDERS`: openai/openrouter/ollama; `IMAGE_PROVIDERS`: openai/gemini/zai/ollama), every field cited to its pre-existing source. `storage/app_state/defaults.py` and `config.py` now derive every provider constant / env-var fact from the registry (byte-identical values, pinned by a 13-test `test_provider_registry.py` consistency suite incl. a three-source `supports_reference_images` agreement check across the registry field / `PROVIDER_SUPPORTS_REFS` / each provider class's ARC-115 attribute). The TUI (settings `ImageProviderSection`, style-gallery, wizard fallback), `images/provider_factory.py:resolve_image_base_url` (`default_base_url`), and `storygen_api/security.py:_PROVIDER_VALIDATORS` (`allows_loopback_base_url` — SSRF host allowlist stays put) all read from it. New token-gated `GET /api/providers` exposes the registry (env-var *names* only, never values); `PUT /api/settings` now rejects unknown provider ids with 400 (hardens SEC-002). The web settings + style-gallery pages fetch `/api/providers` and render dropdowns from it (`api-types.gen.ts` regenerated; page-render tests pin the wiring). `make checkall` green (968 Python + 68 web). Adding a provider is now a one-registry-entry (+ provider-class) change. Accepted follow-ups: the web `IMAGE_LABEL_MAP` preserves a pre-existing shortened-label divergence (converge labels separately); the Gemini base-URL placeholder branch + Ollama advisory remain explicit id-compares with registry-citing comments (genuine SDK/runtime quirks, not registry-owned facts); `fallback_provider` PUT validation is a natural next step now that the registry exists.

### ENH-006 — Opt-in TTS audio pregeneration during prefetch
Branch prefetch already background-generates pending choices' beats and images; audio is the one asset still generated on demand (first `speak` per node blocks on the TTS provider). Extend `PrefetchCoordinator` with an opt-in "pregenerate audio" setting (default off — it spends provider credits speculatively) that synthesizes the prefetched node's narration MP3 into the existing per-node audio cache using the current TTS prefs, so picking a prefetched choice plays instantly.
**Impact**: Medium — removes the last visible latency for TTS users on the happy path. **Effort**: Medium (coordinator + settings toggle + cache-key reuse; careful cost gating).

> **✅ DONE (2026-07-17).** Added a shared `src/storygen/tts/cache.py:synthesize_to_cache` facade (state-safe — delegates to `TTSPlayer.generate()`, never touches playback state) plus a per-node `asyncio.Lock` registry keyed by `(game_id, node_id)` so concurrent synth for the same node is exactly one provider call: both the prefetch path and `PlayScreen._speak_current_node` funnel through the lock, and `generate()`'s cache-exists check + atomic tempfile+`replace` write run inside it (so the second caller short-circuits and a reader never sees a half-written MP3). New opt-in `TTSPrefs.pregenerate_prefetch_audio` (default OFF) surfaced in TUI + web Settings (no save migration — `TTSPrefs` lives in `app_state.json` with a permissive read). `PrefetchCoordinator` hooks it: after a prefetched node's beat commits (outside the LLM semaphore so a slow TTS call doesn't pin a slot), if the pref is on and a player is configured, it synthesizes the narration MP3 into the per-node cache and persists `node.tts_audio_path`; failures are swallowed at debug-log and never fail the prefetch. Note the API server never wires a `TTSPlayer` (`deps.py` constructs `BeatPipeline` without one), so the synth gate short-circuits there and the per-process lock registry is session-scoped to the TUI. Changing voice/provider after a prefetch only wastes one synth — the cache key invalidates cleanly (no audible drift). `make checkall` green (968 Python + 68 web), incl. a concurrent same-node race test asserting exactly one provider call. Follow-up: a bounded/evicting lock registry if the TUI process ever becomes long-lived across many games.

### ENH-007 — Web code-splitting + render optimization
After QA-001/002 decompose the two 1,200-line pages into modals + hooks, the natural follow-on: load each modal with `next/dynamic` (they're invisible 95% of the time), memoize the heavy tree/graph components (`StoryGraph`'s `TreeNodeBox`, CC 19, re-renders on every store change), and narrow Zustand selectors so token/beat updates don't re-render the whole page. The par-mem graph shows `Button.tsx` with in-degree 83 — the shared UI layer is fine; the waste is at the page level.
**Impact**: Medium — smaller initial bundle, smoother streaming updates (compounds ENH-002). **Effort**: Low (~half session, but strictly after QA-001/002).

> **✅ DONE (2026-07-17) — partial (dynamic modals landed).** Converted the 9 play-page modals (`CharacterDetailModal`, `EditImageModal`, `EndingsModal`, `ExportBookModal`, `PortraitsModal`, `RecapModal`, `RelationshipsModal`, `ReplayModal`, `StoryGraphModal`) and the 3 characters-page modals to `next/dynamic({ ssr: false })` in `web/src/app/play/[gameId]/page.tsx` and `web/src/app/characters/page.tsx`, so their code splits out of the initial bundle and loads on first open. DEFERRED from this pass: `React.memo` on `TreeNodeBox`/per-node leaves and Zustand selector narrowing (`useShallow`) — those are lower-payoff and the existing store call sites already use per-field selectors in the hot paths; pursue them in a follow-up if streaming (ENH-002) makes re-renders visible.

### ENH-008 — API observability: timing + provider-latency logging
The API logs exceptions but nothing about normal operation: no request timing, no provider-call latency, no per-game cost trail beyond the save totals. Add a small ASGI timing middleware (method, route template, status, duration) and wrap the shared adapters with debug-level provider-latency logs (model, duration, token counts already flow through `_on_usage`). Structured (`extra={}`) so it's grep/jq-able; no new dependencies.
**Impact**: Low-Medium — makes "why was that advance slow" answerable and gives cost/latency history for provider tuning. **Effort**: Low (~half session).

> **✅ DONE (2026-07-17).** Added an HTTP request-timing middleware to `src/storygen_api/main.py` (logs `request` at INFO with `method`/`path`/`status`/`duration_ms`, timing the failure path too); WS-advance timing in `routers/ws.py` logs `ws advance` at INFO with a truncated `game` id (`game_id[:8]`) and `ok` flag; the three pydantic-ai adapters (`BeatAgentAdapter`/`IllustrationAdapter`/`SummaryAdapter` in `runtime/adapters.py`) now log `agent call` at DEBUG with `agent`/`duration_ms`/`input_tokens`/`output_tokens` (best-effort token extraction). `_configure_logging()` tunes `storygen_api` (INFO) and `storygen` (WARNING — keeps the TUI's shared modules silent) from `STORYGEN_LOG_LEVEL` (documented in `.env.example`). All logging is structured via `extra={}`; no new deps. Covered by `tests/unit/test_api_observability.py` (4 tests: middleware success/failure, adapter latency, log-level config). `make checkall` green (926 + 62 tests).
